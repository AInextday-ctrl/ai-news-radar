Codex 如何在您的机器上运行命令并限制您的控制。

在 OpenAI，我们在保护代理方面采取深度防御⁠（在新窗口中打开）方法。虽然我们在培训和协调方面的投资是这项工作的基础，但我们还在代理工具 Codex（在新窗口中打开）中实施了功能，以提供额外的保护。由于 Codex 所做的最常见（且有潜在风险）的事情之一是在您的计算机上运行命令，因此我们构建了 Codex 沙箱，以便 Codex 可以在您控制的文件系统和网络限制内的现有环境中工作。

沙盒（在新窗口中打开）限制程序运行时可以访问的内容。对于照片组织任务，您可以配置 Codex 沙箱，让命令读取和修改 ~/Pictures 中的文件，同时阻止网络访问以防止上传。对于代码审查，您可以允许访问在线文档，同时保持源文件只读。用户通过 ⁠(opens in a new window) 权限配置文件 ⁠(opens in a new window) 配置 Codex 沙箱，该配置文件定义了 Codex 会话的文件系统和网络限制。

在本文中，我们将从 Codex 沙箱默认值背后的权衡开始，然后解释沙箱的设计以及工具如何使用它来运行命令。我们将展示最终用户和企业如何根据自己的需求定制其权限，以及开发人员如何在自己的工具中重用沙箱。最后，我们将研究如何在 macOS、Linux 和 Windows 上实施这些限制。

在 Codex 中，我们的理念是为沙箱指定保守的默认值，但仍能实现有意义的工作。例如，使用 Git 存储库作为工作区根目录，内置 :workspace 权限配置文件：

允许在工作区中写入，同时保持 .git 和 .codex 等目录只读。这使得 Codex 可以编辑源代码，而无需每次更改都寻求许可，同时防止直接更改 .codex/config.toml 或 .git/hooks 下的 Git 挂钩。

允许广泛的文件系统读取，但取决于用户现有的操作系​​统权限。编译器、运行时和构建工具依赖于存储库外部的 SDK、库和配置。限制对工作区的读取会破坏许多普通的工作流程。代价是机器上其他地方的敏感文件也可能保持可读（例如包含 API 密钥的配置文件）。

禁用网络访问。这会阻止直接上传到外部服务，包括尝试窃取命令可以读取的数据。它还会阻止合法操作，例如下载依赖项，这需要额外的访问权限。

这些限制可以防止大量不良行为，但有害行为仍然可能发生。例如，代理可以将恶意代码注入本地安装的包（例如node_modules/prettier）中。这样的更改可能不会出现在 git status 中，因为 node_modules 通常被 Git 忽略。如果用户的编辑器在保存时运行该 Prettier 副本，则只需保存文件就可以在 Codex 沙箱之外执行恶意代码。这就是我们采取深度防御方法的原因：沙箱限制可以访问的命令，而训练和对齐帮助模型根据用户的意图使用该访问权限。

有关定制沙箱权限并将其与企业环境中的其他保护相结合的指南，请参阅 Codex 安全指南⁠（在新窗口中打开）。

虚拟机和容器⁠（在新窗口中打开）是用于沙箱的两种流行机制，但我们对 Codex 沙箱采取了不同的方法。 Codex 没有将计算转移到单独的环境中以提供隔离，而是使用每个平台的沙箱设施来限制在用户现有环境中运行的命令。对于许多开发人员来说，他们的笔记本电脑充当定制的开发环境，他们可以随意更改。在 Docker 容器中复制该环境可能需要一些工作，并且某些工作流程仍然依赖于主机上运行的工具。

例如，考虑使用 Codex 在 Mac 上开发 iOS 应用程序。如果您决定通过在 Docker 中运行 Codex 来对 Codex 进行沙箱处理，Codex 将无法运行由本机 Mac 可执行文件组成的 iOS 构建工具链，也无法启动 iPhone 模拟器来运行代码。基于 Docker 的工作流程可以将构建和模拟器操作委托给 Mac 主机，但这些操作将在容器的沙箱之外执行，并且需要它们自己的限制。对于 Codex，我们更愿意通过大力投资特定于操作系统的沙箱来让事情变得简单，以便 Codex 可以在最适合手头任务的环境中运行。
