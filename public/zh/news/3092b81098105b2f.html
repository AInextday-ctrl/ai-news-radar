OpenAI 官方动态 权威实录

我们由 Codex 支持的系统可以自动查找和修复性能问题。

代理开发的惊人速度使得传统的性能工程方法变得不可持续。为了跟上步伐，我们构建了 Performance Factory，这是一个自治系统，它利用 Codex 和我们的模型的全部功能以前所未有的速度查找和修复回归。 Performance Factory 在云中运行并自动调查和解决性能问题，使我们能够跟上路线图的雄心壮志。

在 Performance Factory 中，我们的工程师为重复性作业定义工作流程，并为执行这些作业的 Codex 代理编写指令。特别是，当性能警报触发时，回归工作流程会打开一个任务。代理调查减速情况，将其发现记录在任务中，并提出修复方案供工程师审查。部署后，另一个代理将执行相同的任务来检查性能是否已恢复到基线。从调查到编写修复程序再到验证缓解措施，性能工厂中的第一个工作流程已经自动化了修复回归的整个过程。在短短三个多月的时间里，回归工作流程跟踪了 1,700 多项调查，找出了 600 多个案例的根源。每天有 17 项自动调查。

在这里，我们将分享我们对 Codex 的使用如何演变为现在的 Performance Factory，逐步完成我们的第一个运行工作流程，并分享在生产中构建和运行代理工作流程的早期经验教训。

当我们使用 Codex 进行更多性能工作时，我们注意到我们团队的工作方式取得了进步。我们希望其他服务团队在其他领域采用代理工作流程时可以从我们的流程中学习。

1. 食品法典委员会之前。在 Codex 之前，工程师手动检查指标和日志、比较跟踪、调试实时机器并读取代码以调查速度下降情况。这项工作非常耗时，并且知道在哪里查找通常需要对服务有深入的了解。相关信号很容易被忽视。当我们反复遇到相同类型的问题时（例如 ChatGPT 的第一个令牌延迟中的回归），我们构建了高级工具，例如 CPU 和分配分析器，以使这些调查变得更容易。随着时间的推移，我们积累了 30 多个性能工具。

2. 法典作为合作伙伴。一旦我们与 Codex 成为合作伙伴，工程师就会问：“为什么速度变慢了？”并与 Codex 合作进行调查，即使是在不熟悉的系统中。 Codex 可以搜索大型代码库，查找相关指标和跟踪，跟踪跨服务的交互，并进行适当的分析以拼凑发生的情况。但工程师仍然必须掌控整个过程，了解要使用哪些性能工具以及如何指导调查。对于更多的人来说，困难的调查更容易调试，所需的专业知识和时间更少。

3.可重复使用的技能。为了进一步自动化，我们通过称为性能取证的共享技能捕获了性能团队的调查过程。它告诉 Codex 哪些工具可用、何时使用它们以及如何解决速度下降的问题，以便 Codex 可以尝试从几个角度解决问题：

我们使用基于过去回归的评估来测试和完善性能取证技能。对于我们关注的回归类型（例如，ChatGPT 延迟和可用性下降），我们现在可以向 Codex 发出警报并在一次运行中获得诊断结果，而无需引导它完成每个步骤。

4. 人类代理。当我们添加和完善与性能相关的 Codex 技能（例如性能取证）时，我们开始感觉自己是警报和 Codex 之间的代理。警报将被触发，工程师只需使用正确的技能将其复制并粘贴到 Codex 中，然后将结果粘贴回 Slack 中。

5. 自动化调查。接下来，我们将调查转移到云端，以便警报可以自动启动 Codex 会话。 Codex 调查了速度下降的情况，并将其调查结果发布在 Slack 线程中，但自动化以该回复结束。工程师仍然必须进行诊断，开发修复程序，并在部署后检查它是否有效。随着警报的积累，甚至弄清楚哪些回归需要注意也意味着要筛选 Slack 线程。

6、工厂。我们构建了 Performance Factory 来运行端到端代理性能工程工作流程。它跟踪每个活动任务接下来需要什么，并在该步骤准备好时分配一个代理。每个任务都会保留其状态和结果，因此工作可以在代理和工程师之间传递，并在代码审查或部署后恢复。对于回归，工作从调查警报开始，到验证生产中的恢复结束。我们可以将常见的优化转化为在我们的服务中定期运行的工作流程。发现潜在优化的工作流程可以在另一个工作流程中打开任务来测试和实施它。

任务服务是工程师通过添加用 Markdown 编写的配置文件和提示以供代理遵循的提示来定义工作流程的地方。配置列出了任务可以经历的状态、允许的转换以及哪些步骤需要工程师。单独的提示告诉代理在每一步要做什么。

1code-change/2├── config.toml3└── work/4 ├── Implementing.md5 └── reviewing.md 代码更改任务包含一个配置文件，以及实现和审核的 Markdown 提示。
