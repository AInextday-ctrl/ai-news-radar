Anthropic 权威实录

许多问题都存在生成器与验证器之间的差距：验证解决方案是否正确通常比提出解决方案要容易得多。数独就是一个典型的例子。检查解决方案很简单（只需计算每行、每列和框中的数字），但找到该解决方案可能需要很长时间。许多雄心勃勃的 Claude 项目都依赖于这一差距：只要有可靠的方法来验证其工作，Claude 就可以承担数学证明的形式化或迁移大型、经过良好测试的代码库的任务。

但随着 Claude 的能力越来越强，它开始在实时系统中承担项目，在这些系统中，生成工作比验证工作更容易。在这些系统中，用户经常依赖于测试套件之外的边缘情况和怪癖，并且很难编写涵盖所有内容的“正确”定义。如果没有可靠的方法来检查 Claude 的工作，实时系统的迁移就很难令人信任——无论 Claude 生成代码的速度有多快。

当我们将 Messages API 从 Python 迁移到 Rust 时，我们遇到了这个问题。此 API 是客户以及我们自己的应用程序（例如 Claude Code 和 Cowork）联系 Claude 的主要方式。从 2024 年初到 2026 年秋季，API 流量增长了大约 1,800 倍。 Rust 可以让我们在每个请求中使用更少的 CPU。 Claude 在大约一周内编写了 API 核心请求路径的第一个版本。但是在迁移中建立信任需要我们找到一种方法来验证我们的 Rust API 与我们的生产 API 是否相同。事实证明，这很困难，原因有几个，包括 Python API 在整个迁移过程中不断变化，因此奇偶校验是一个不断变化的目标；克劳德可以不确定地回复同一请求，因此两个输出之间的差异并不一定意味着存在错误；而且我们无法读取客户的请求，因此我们无法轻松看出两个版本的差异在哪里。

在这篇文章中，我们分享了如何将生产 Messages API 本身转变为验证器，以及如何帮助我们在生产流量上测试新的 Rust 版本，找到不同之处，并自动调度代理来修复这些差异。这使我们能够在 Rust 上发布一个 API，每个请求使用的 CPU 减少约 70%，并将第一个令牌的中值时间缩短约 20%，而无需使服务离线或冻结功能开发。

我们于 2023 年构建了 Messages API 并用 Python 编写，该 API 在我们的大部分研究代码中广泛内部使用。起初，这很简单。消息 API 将请求传递给模型并发回模型写入的内容。 （当时的一位工程师称其为“基本上是一个请求转发器”。）但是，随着 Messages API 的功能变得越来越强大，并且与我们的代码库深度集成，它还与我们的研究和推理团队拥有的 Python 库开发了共享依赖项，这使得移动变得困难。如果我们想转向另一种语言，就意味着重新构建日志记录、指标和工具。

这种计算逐渐开始改变。到 2025 年底，每个 Messages API 请求都必须经过验证、转换为提示、标记化并由我们的安全分类器进行筛选。当每个回复到达时，令牌流必须被分类为文本、思考和工具调用，而 Python 每次创建对象、释放内存或将工作交给下一个任务时，都会给每个步骤增加开销。流量最终增长远远超出了最初构建 Python 服务的目的（图 1），我们很快需要找到一种方法来提高服务效率。

增量还是一次性？

出于至少两个原因，通常会谨慎地进行大型生产系统的完全重写。首先，不能保证测试套件覆盖 100% 的生产代码行为，并且重写它是有风险的。其次，所需的巨大努力往往使此类工作变得棘手。 （2024 年，在我们的一位工程师建议迁移到 Go 或 Rust 后，另一位工程师暂时解决了这个问题：“我们不会用 Go 或 Rust 重写 API！”）

因此，如果您正在寻求性能提升，标准建议是仅重写那些降低系统速度的部分，这就是我们的起点。在 Rust 中，我们重写了解析模型输出的代码并从 Python 中调用它。这使 API 的 CPU 使用率降低了约 8% 到 10%。然而，渐进式解决方案通常会增加复杂性，因此确保渐进式改进能够证明这些成本的合理性非常重要。在我们的例子中，收益并不能证明增加的复杂性是合理的。现在，每个令牌在 Python 和 Rust 之间交叉了 3 次（图 2），从而产生了新的开销来源。

随着克劳德的能力越来越强，我们开始质疑避免全面迁移的通常理由是否仍然成立。开展该项目所需的工作量正在迅速下降：到 2026 年 5 月，Claude 编写了 Anthropic 合并的 80% 以上的代码。我们想知道 Claude 现在是否可以帮助我们编写代码，以凭经验捕获生产系统中的每个行为和修复。但问题是：我们如何验证我们的迁移行为是否正确？验证而非生成已成为瓶颈。

我们如何验证迁移

为了验证迁移，我们首先需要定义“正确”的含义。您可以通过多种方式来完成此操作（图 3）。如果幸运的话，您可以简单地编写一条规则。数学中的定理是一个精确的陈述，证明助手（如 Lean）可以根据一组固定的规则检查证明的每一步。其他时候（在软件工程中更常见），您可以通过一组示例（例如测试）来定义“正确”。例如，当 Bun 从 Zig 迁移到 Rust 时，其测试套件是用 TypeScript 编写的，因此相同的测试可以判断两个版本。在我们的案例中，这两种方法都不够，因此我们使用现有系统作为预言机来在迁移过程中测试奇偶校验。在这种情况下，我们现有的系统（消息 API）不断变化。我们定期发布新型号并发布新功能，这使得“正确”的定义成为一个不断变化的目标。

测试是我们最容易开始的地方，因为我们已经有一组约 700 个集成测试。然而，有两个问题限制了我们信任他们来验证如此高风险的迁移正确性的能力（图 4）。

这些测试与Python实现耦合在一起。集成测试发送请求，然后检查应答和发送给其他服务的内容。我们的测试在测试进程中运行Python API，并在Python的内存中模拟计费和速率限制等服务。测试必须随着代码的变化而变化，克劳德在这两方面都提供了帮助。现在，“通过”可能意味着代码是正确的，或者测试已经被更改为允许错误代码通过的方式。我们看到了这种情况：当我们审计移植的测试时，我们发现了100多个弱化的断言。
