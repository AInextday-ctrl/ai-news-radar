OpenAI Full Report

How Codex runs commands on your machine with limits you control.

At OpenAI, we take a defense in depth⁠(opens in a new window) approach when it comes to safeguarding agents. While our investments in training and alignment are fundamental to this effort, we also implement features in our agentic harness, Codex⁠(opens in a new window), to provide additional protections. Because one of the most common (and potentially risky) things Codex does is run commands on your computer, we built the Codex sandbox so Codex can work in your existing environment within filesystem and network limits you control.

A ⁠(opens in a new window)sandbox⁠(opens in a new window) limits what a program can access while it runs. For a photo-organizing task, you might configure the Codex sandbox to let commands read and modify files in ~/Pictures while blocking network access to prevent uploads. For code review, you might allow access to online documentation while keeping source files read-only. Users configure the Codex sandbox through ⁠(opens in a new window)permission profiles⁠(opens in a new window), which define the filesystem and network restrictions for a Codex session.

In this article, we’ll start with the tradeoffs behind Codex’s sandbox defaults, then explain the sandbox’s design and how the harness uses it to run commands. We’ll show how end users and enterprises can tailor its permissions to their needs and how developers can reuse the sandbox in their own tools. Finally, we’ll examine how these restrictions are enforced on macOS, Linux, and Windows.

In Codex, our philosophy is to specify conservative defaults for the sandbox that still enable meaningful work. For example, with a Git repository as the workspace root, the built-in :workspace permission profile:

Allows writes within the workspace, while keeping directories such as .git and .codex read-only. This lets Codex edit source code without seeking permission for every change, while preventing direct changes to .codex/config.toml or Git hooks under .git/hooks.

Allows broad filesystem reads, subject to the user’s existing OS permissions. Compilers, runtimes, and build tools depend on SDKs, libraries, and configuration outside the repository. Restricting reads to the workspace would break many ordinary workflows. The tradeoff is that sensitive files elsewhere on the machine may also remain readable (such as config files containing API keys).

Disables network access. This blocks direct uploads to external services, including attempts to exfiltrate data the command can read. It also prevents legitimate operations such as downloading dependencies, which require additional access.

These restrictions prevent a large class of bad behavior, but harmful actions are still possible. For example, the agent could inject malicious code into a locally installed package such as node_modules/prettier. Such a change might not appear in git status because node_modules is often ignored by Git. If the user’s editor runs that copy of Prettier on save, simply saving a file could execute the malicious code outside the Codex sandbox. This is why we take a defense in depth approach: the sandbox limits what commands can access, while training and alignment help the model use that access in accordance with the user’s intent.

For guidance on tailoring sandbox permissions and combining them with other protections in an enterprise environment, see the Codex security cookbook⁠(opens in a new window).

Virtual machines and containers⁠(opens in a new window) are two popular mechanisms used for sandboxing, but we take a different approach with the Codex sandbox. Instead of moving computation to a separate environment to provide isolation, Codex uses each platform’s sandboxing facilities to constrain commands running in the user’s existing environment.For many developers, their laptop serves as a bespoke dev environment that they can change on a whim. Reproducing that environment in a Docker container can take work, and some workflows still depend on tools that run on the host.

For example, consider using Codex to develop an iOS app on a Mac. If you decided to sandbox Codex by running it inside Docker, Codex would not be able to run the iOS build toolchain composed of native Mac executables, nor could it launch the iPhone simulator to run the code. A Docker-based workflow could delegate builds and simulator operations to the Mac host, but those operations would execute outside the container’s sandbox and would need their own restrictions. For Codex, we prefer to keep things simple by investing heavily in OS-specific sandboxing so Codex can run in the environment that is most appropriate to the task at hand.

The harness exposes these OS-specific sandboxing mechanisms through a common API across macOS, Windows, and Linux. This API takes a command and a permission profile. If the permission profile allows limited network access, the caller must supply a network proxy to enforce those limits:

1# This is a simplified version of the actual API.2def spawn_command_under_sandbox(3 program_and_args: list[str],4 cwd: Path,5 env: dict[str, str],6 permission_profile: PermissionProfile,7 network_proxy: NetworkProxy | None,8) -> Child:This function starts the process in a sandbox and returns a Child handle the harness can use to wait for it to finish. Each child process inherits its parent’s sandbox constraints, so those restrictions apply throughout the process tree initiated by the command, even to descendants that outlive the original process.

Next, we’ll look at how permission profiles are defined.

A named permission profile lets you reuse the same filesystem and network restrictions across projects. You can define your own profiles under [permissions] in config.toml. For example, the following defines a profile named dev that extends⁠(opens in a new window) the built-in :workspace profile:

1# Use the dev profile by default.2default_permissions = "dev"34[permissions.dev]5# This is displayed when /permissions is run in the Codex CLI.6description = "Development with extra read-only protections."78# A profile can be derived from an existing profile.9# Profiles starting with ":" are provided by Codex.10extends = ":workspace"1112[permissions.dev.filesystem]13"~/build-cache" = "write"1415[permissions.dev.filesystem.":workspace_roots"]16".devcontainer" = "read"17".vscode" = "read"18"**/*.env" = "deny"19"secrets" = "deny"The dev profile adds write access to ~/build-cache and places additional restrictions on files in the workspace. Filesystem entries can grant read-only access (read), grant read and write access (write), or block access entirely (deny).

The :workspace_roots table lets you define rules for paths relative to a project’s workspace roots. By default, the Codex CLI uses its working directory as its sole workspace root, while the ChatGPT desktop app uses the project’s source folders. Codex applies each rule to every root, so the .vscode entry in dev makes the .vscode directory read-only under each root.

Individual users can configure defaults that apply across projects and override them for a particular trusted project. Enterprise administrators may also want to configure defaults for their users and constrain which settings those users can change. Codex supports both through layered configuration and managed requirements.

As described in Configuration precedence,⁠(opens in a new window) Codex merges settings from multiple config.toml files. Tables are merged recursively, with the higher-precedence source winning when values conflict. Arrays are replaced as a whole.

This is why permission profiles use tables for filesystem paths and network domains. A team can add or override individual entries in its own configuration and automatically inherit changes to all other entries in the organization’s base configuration:

1[permissions.dev.filesystem.":workspace_roots"]2".idea" = "read"34[permissions.dev.network.domains]5"example.com" = "allow"Administrators can also supply managed requirements⁠(opens in a new window) through requirements.toml to constrain users’ configuration choices. These requirements can come from multiple sources, including system files and cloud-provided policy. A common use case is to specify allowed_permission_profiles to constrain the set of permission profiles an enterprise user can select. For example, an administrator could specify these cloud requirements:

1default_permissions = ":read-only"23[allowed_permission_profiles]4":read-only" = true5":danger-full-access" = falseThe cloud requirements would take precedence over the system requirements file at /etc/codex/requirements.toml, so an entry in that file cannot override the explicit ":danger-full-access" = false above. Leaving :workspace unspecified allows another requirements layer to supply that entry. Profiles whose entries are false or absent from the final merged table are unavailable.This separation lets organizations enforce limits while users tailor their configuration within those limits. The resulting permission profiles can be used by the harness or applied directly to a command, as we’ll see next.

The Codex CLI provides a sandbox command to facilitate running an arbitrary command under a permission profile defined in the Codex config. This is commonly used to test out the profile, ensuring that the sandbox prevents the behavior it was designed to block.

For example, the following command attempts to configure VS Code to run a malicious auto-formatter on save. Assuming .vscode already exists, the dev profile defined above should block this write because that directory is read-only (codex sandbox treats cwd as a workspace root by default):

1bash: .vscode/settings.json: Operation not permittedThe codex sandbox command makes Codex’s sandboxing mechanism available independently of an agent session. You can use the same configuration language and platform-specific enforcement to constrain commands launched by your own tools.

For a stdio MCP server configured in config.toml, the Codex harness does not attempt to sandbox the command used to start the server. Codex cannot reliably infer which files or network services that server needs, so applying a default sandbox profile could break an otherwise valid configuration.

The sandbox implementation turns a permission profile into restrictions enforced by the operating system. The network proxy’s core request-handling and policy logic is shared across all three major operating systems, while proxy setup and integration with the sandbox are OS-specific. We’ll examine the shared proxy first, followed by the implementations for macOS, Linux, and Windows.

To enforce a permission profile’s network restrictions, the harness starts a network proxy and configures the sandbox to allow connections to it while blocking direct connections to external hosts. The proxy checks each request against the profile’s domain rules to determine whether to forward it.

In the Codex repo, the network proxy is implemented in the codex-network-proxy⁠(opens in a new window) crate, which the harness uses as a library, though it can also be built as a standalone CLI⁠(opens in a new window). When enabled, codex-network-proxy starts both an HTTP proxy and a SOCKS5 proxy by default. These proxy addresses are communicated to the process spawned by the sandbox via environment variables. In addition to injecting standard environment variables such as HTTP_PROXY, HTTPS_PROXY, and ALL_PROXY, a number of well-known application-specific environment variables⁠(opens in a new window) (such as PIP_PROXY) are injected, as well. Admittedly, not all programs honor these environment variables. If a program attempts a direct connection to an external host, the operating system’s sandbox restrictions block it, as described in the platform-specific sections below.

The network proxy is responsible for implementing the network restrictions defined in a permission profile. For example, the dev profile shown earlier allows requests to *.openai.com and explicitly denies requests to evil.example. When a request targets a domain that does not match an allow or deny rule, the proxy can suspend the request while it delegates to the harness for approval. Like the shell command example, Codex may prompt the user directly, or it might route the request to auto-review⁠(opens in a new window). Upon receiving a decision, the proxy either allows the request to proceed or rejects it with an error response.

The order matters here because even a DNS lookup can leak information encoded in a hostname. The proxy therefore resolves the requested hostname only after determining that it is allowed or approved. Note that broad wildcard rules or access to DNS services can still permit DNS-based exfiltration.

On macOS, Codex uses Seatbelt⁠(opens in a new window), Apple’s kernel-enforced sandboxing mechanism. Seatbelt policies are written in Sandbox Profile Language (SBPL), a Scheme-based language for expressing sandbox restrictions. Codex invokes Seatbelt through macOS’s /usr/bin/sandbox-exec command. Like codex sandbox, it takes options describing the sandbox followed by the command to run:

1sandbox-exec -p PROFILE [-Dkey=value]* -- PROG ARGS...The PROFILE is a string of SBPL that contains entries that configure the sandbox. For example, the following SBPL snippet makes /dev/null and /dev/zero readable and writable under the sandbox policy:

1; local HTTP proxy launched by Codex2(allow network-outbound (remote ip "localhost:3128"))34; local SOCKS proxy launched by Codex5(allow network-outbound (remote ip "localhost:8081"))Codex’s base profile starts with (deny default), so outbound connections remain blocked unless explicitly allowed.

1; Pass -DWRITABLE_ROOT_0=/path/to/dir to specify a folder that cannot be removed.2(deny file-write-unlink3 (require-all4 (literal (param "WRITABLE_ROOT_0"))5 (vnode-type DIRECTORY)))which are populated by the -Dkey=value options passed to sandbox-exec.

To implement its own sandbox API, Codex builds up the list of arguments⁠(opens in a new window) to sandbox-exec starting from a base policy⁠(opens in a new window), and then uses permission_profile and other context to amend it to produce the complete Seatbelt profile. The resulting profile and accompanying -D arguments configure the restrictions enforced by Seatbelt, while the network proxy enforces additional network rules. With the full arg list assembled, the invocation of sandbox-exec is straightforward.

Generating the correct SBPL is challenging because Apple does not document the language for third-party use. Indeed, man sandbox-exec states The sandbox-exec command is DEPRECATED (as is the sandbox_init() library function documented via man 3 sandbox_init). Despite the deprecation warning, macOS still ships Seatbelt profiles in /usr/share/sandbox, and third-party software, including Google Chrome and Chromium⁠(opens in a new window), continues to rely on Seatbelt. As such, we plan to continue to use Seatbelt for the foreseeable future.

To create the sandbox on Linux, Codex uses a combination of bubblewrap⁠(opens in a new window) (bwrap), a command-line tool for constructing isolated environments, and seccomp-bpf⁠(opens in a new window), a Linux kernel mechanism for filtering system calls. An internal helper named codex-linux-sandbox coordinates the setup. Like sandbox-exec on macOS, it takes a sandbox configuration followed by a command to run:

1codex-linux-sandbox SANDBOX_ARGS... -- PROG ARGS...When filesystem isolation or proxy routing is required, codex-linux-sandbox invokes bwrap to create the initial sandbox environment. bwrap then launches codex-linux-sandbox --apply-seccomp-then-exec inside it. This second invocation uses seccomp-bpf to apply additional restrictions before running the user’s command.

To construct that initial sandbox environment, Codex uses bubblewrap to create a filesystem view in a separate mount namespace that reflects the permission profile’s filesystem rules. Because this is fundamental to the sandbox implementation, Codex vendors its own copy of bwrap in case the user has not installed their own, but it prefers a compatible installation of ⁠(opens in a new window)bwrap⁠(opens in a new window) found on PATH, when available. Empirically, some Linux distributions disable access to user namespaces by default⁠(opens in a new window), but grant an exception for the system bwrap.
