Show HN: Neui – Go web apps with a built-in AI agent

✍️ By derstruct

Neui has launched an integrated stack that combines a Go-based web framework (Doors) with an AI agent. By allowing developers to annotate UI elements, the agent can interact with the page, execute backend scripts, and automate workflows natively without the need for additional API layers or state synchronization.

⚡ Executive Summary & Key Facts

  • [Core Event] Neui development team (Go ecosystem and Web dev tooling): Launched an AI-integrated web stack with native UI interaction and workspace capabilities.
  • [Root Cause & Mechanism] To eliminate the friction of building API-heavy AI agents by binding UI logic directly to backend tools.
  • [Key Technical Spec] Uses Doors framework for single-stack execution of Go apps and AI agents.
  • [Key Position & Outlook] Optimizes context caching to reduce operational costs for AI-driven interactions.

📰 Full In-Depth Coverage

Hacker News Full Report

Neui is an AI agent and a web framework built as one stack. The framework, Doors (Apache-2.0), lets Go teams build modern interactive apps with no separate frontend and no API layer. Neui adds the agent: it runs inside the user's session, sees the parts of the page you let it see, operates the UI like a user, and brings its own work environment for the jobs a chat alone cannot do.

Every feature you build for users is instantly usable by the agent, with a work environment powerful enough to automate the work your users do by hand.

Developers mark which parts of the page the agent may see and use, right in the existing markup. The agent then clicks, types and reads like a user, and the app's own logic runs. There is no per-action code to write and no state to mirror.

A tool is one Go function that runs on the server, with no endpoint or permission code to write. Developers decide what the agent can see and do right where they build the UI, so its access is scoped to each user and updates with the screen.

The agent gets its own file workspace, scripts that run bulk UI work in one step, spreadsheets, web search, MCP connectors, background tasks, and automatic handling of long conversations. One script can call every tool and work across the whole UI in a single step.

When a user needs functionality your UI doesn't have, the agent builds it on the spot, anything from a single screen to a specialized app. It runs in the page with the user's permissions, and the agent stays in the loop to make the decisions.

Your users get the chat experience they already know from chat apps, with nothing to build or purchase.

The conversation is prompt-cache friendly, so input costs an estimated 6 to 14 times less than in copilots that rebuild the prompt for every screen, depending on the provider's cache pricing. Built-in scripts do bulk work without extra model turns or context bloat.

The conversation, instructions and tools live on the server, and the browser sends only the user's new message. A tampered browser can't add tools, rewrite history or change what the agent is told.

Every open page runs on the server, integrated with the agent harness. You mark in the page template what the agent may see and use.

Works the real UI. The agent reads, fills and clicks the elements you mark, as the user would, and your handlers run as usual. There's no state to mirror and no action to re-implement.

~>neui.Use{ Desc: "Customer's email", // RW: the agent reads the value in the user's browser or writes its own. Rights: neui.RW, } <input type="email" name="email"> Tools in the template. Register agent tools right in the page template, based on the UI context and the user's permissions.

~(if user.IsAdmin() { ~neui.Tool[Refund, Receipt]{ Name: "refund", Desc: "Refund the order", Handler: orders.Refund, } }) Persistent tools. Go functions registered for the whole app or for one session are available in every chat. The built-in work environment works the same way.

crm := neui.NewModule("crm", "Customer records of the signed-in user") crm.Tool("find", "Find a customer by name or email", customers.Find) Page context. Attach data to a part of the page to tell the agent what it shows, such as the records in a view or hints on how to use it.

~neui.Data{ Text: "Open orders of this customer", Object: orders, } App events. Your app can tell the agent when something happens, such as a payment arriving. An idle agent reacts right away, and a busy one picks it up on its next turn.

neui.Instance(ctx).Emit(ctx, "payment_received", map[string]string{"invoice": id}, nil) Stays in sync without token waste. The framework tracks tools, data and elements as the page changes, and the agent reads them only when it needs to.

An agentic app is a program the agent writes and runs for the user in an island, a region of the page. You declare the island in the page template and give it the components and Go functions its apps may use.

~neui.Island{ Name: "workbench", Desc: "Apps for the user's invoice work", Template: func(slot gox.Comp) gox.Elem { return <section>~(slot)</section> }, Library: func(l neui.Library) error { l.Tool("overdue", "Overdue invoices, one page at a time", invoices.Overdue) l.Tool("remind", "Send a payment reminder", invoices.Remind) return nekit.IslandRegisterAll(l) }, } The agent writes a program. It builds an app for the user's request from your component library and the tools you declare, and runs it right away. The model is called only for decisions. The app handles user actions itself and calls the agent only when a decision is needed. The UI stays responsive, no tokens are spent on routine steps, and the agent is still in the loop. Data stays out of the context. The agent works with data through the app's script, without loading it into its context. Data costs no tokens, and text inside it can't steer the agent. App changes on the fly. The user can ask for an extra column, another step or a different check, and the agent updates the running app without losing their work. Runs with the user's permissions. The app is sandboxed and can do only what the signed-in user can, through the components and functions you declared, with no endpoints to build. Widgets included. neui.dev/nekit includes a general-purpose widget set built to cover any business flow, from data entry to review and reporting. It takes your theme from CSS variables, and your own components work alongside it.

Compared with declarative generative UI. In A2UI and similar formats the model describes the screen, and every user action is another model turn. That suits a one-off screen such as a confirmation. An agentic app is cheaper and faster as soon as the user does more than a few things.

Neui ships a complete chat experience out of the box. Use it as is, configure its theme and features, or fork it to build something of your own.

Besides the chat and the page, the agent has a workspace on the server for real work.

The usual alternatives are CopilotKit (plus paid Intelligence), Vercel AI SDK with Sandbox, assistant-ui, OpenAI ChatKit, LangGraph with Agent Server, browser agents and WebMCP. For a Go team each of them means bolting on a React island, CopilotKit and a Node runtime: a second stack.

go get neui.dev Neui is a Go module (neui.dev) that plugs into a Doors app: you configure the agent once with options on the Doors app, turn it on per session once the user is known, and render nekit.Chat on the pages where the user should talk to the agent.

Claude, GPT, Gemini and DeepSeek providers are included, plus a generic one for any server with an OpenAI-compatible Chat Completions API, such as Ollama, vLLM or OpenRouter. SQLite thread storage and disk or S3 upload storage are included too.

Start with the quick start and the back office example, and see the package documentation in doc.go, api/doc.go and nekit/doc.go, and the Doors documentation for building the app itself.

This technical approach signals a shift from 'plugin-based' AI integration to 'native-stack' integration. By binding UI definitions directly to agent logic, Neui minimizes context bloating and latency, offering a potential new paradigm for Go-based enterprise applications that challenges traditional RESTful API architectures in agent-driven workflows.
